### 2.2 The site marks lessons "watched" that were never played
**Files:** `src/YouTubePlayer.jsx:108`, `src/CourseVideoPage.jsx:264`, `src/progress.js:166`

Two separate bugs in the watch-progress sync, both violating your "nothing is invented" rule:

**(a) Fabricated watch history.** When a student leaves a lesson page, the player reports progress to the server — unconditionally, even if the video never started. And that report hard-codes `watched: true`. So merely *opening* a course page and clicking away marks the first lesson watched, permanently, on every device the student signs into.

**(b) Destroyed resume points.** `mergeRemoteEntry` claims in its own comments that it "only ever moves data forward," but it decides by comparing timestamps and never looks at the actual position. I ran the real code: a server row that is one millisecond newer but says "position 0" overwrites a genuine 12-minute resume point with zero.

**What a student experiences:** they open a Physics course, browse the lesson list, come back tomorrow and half the chapter is ticked off as watched. Or they get 12 minutes into a lecture on their laptop, open it on their phone, and it starts from the beginning. Both make the progress feature feel broken and untrustworthy, which is worse than not having it.

**Do this — one line fixes most of it.** In `src/YouTubePlayer.jsx`, inside `reportProgress` (around line 108):
```js
const player = playerRef.current;
if (!player || !playbackRecorded) return;   // <- add !playbackRecorded
```
`playbackRecorded` is already tracked and already resets when the lesson changes. This kills the fabricated ticks at the source. Both existing player tests still pass — I checked; they fire a "playing" event first.

Then, as a backstop, in `src/CourseVideoPage.jsx:264` replace the hard-coded `watched: true` with the real local value: `watched: getWatchedVideoIds(playlistId).includes(videoId)`. **Do not simply change it to `false`** — the sync overwrites the whole row, so a `false` would erase genuinely-watched lessons.

For the resume-point bug, in `src/progress.js:166` require the position to not go backwards as well as the timestamp to be newer. And in `src/progressSync.js:34`, refuse to send a position that isn't a real number rather than defaulting it to 0.

**Also clean up what's already in the database.** Rows written by this bug look like:
```sql
select * from video_progress where watched = true and coalesce(position_seconds,0) = 0;
```
A genuinely-started lesson always picks up a non-zero position, so this is a reliable identifier for the fake ones.

### A8. [MEDIUM] mergeRemoteEntry does not implement its documented "only ever moves FORWARD" contract — a newer server row with a smaller position destroys a real resume point

- **Verdict:** CONFIRMED
- **Category:** n/a
- **Location:** `src/progress.js:166`

**Defect.** mergeRemoteEntry decides whether to apply a server position by comparing timestamps only (`updatedAt > priorPos.at`) and never compares the position values, so a row whose position is 0 but whose timestamp is 1ms newer overwrites a 12-minute local resume point with 0.

**Failure scenario.** I ran this against the real module with a localStorage shim. recordLessonPosition({playlistId:12, videoId:'vidX', seconds:720, duration:2400}) at time T -> getLessonPosition returns 720. Then mergeRemoteEntry({playlistId:12, videoId:'vidX', position:0, duration:null, watched:true, updatedAt:T+1}) -> getLessonPosition returns 0 and the stored entry becomes {t:0, d:null, at:T+1}. The 12-minute resume point is gone. This is reachable two ways in production. (a) An invalid progress report: recordLessonProgressReport (CourseVideoPage.jsx:253-265) calls recordLessonPosition FIRST — which correctly REJECTS a non-finite `seconds` and returns null without writing — and then calls queueProgressSync anyway with that same `position`, and pushNow coerces it: `Number.isFinite(entry.position) ? Math.max(0, entry.position) : 0` (progressSync.js:34). YouTube's getCurrentTime() returns undefined on a YT.Player that has been constructed but has not yet received its ready message, which is exactly the state during the teardown flush when a student clicks a different lesson within ~1s of the page loading, or when the video is embed-blocked/adblocked and the player never becomes ready. Local store: correctly untouched (still t=720). Server row: position_seconds=0, updated_at=now. Next mount, or the student's phone: pull -> mergeRemoteEntry -> updatedAt(now) > priorPos.at(T) -> local position rewritten to 0. The student resumes from the beginning of a 40-minute lecture they were 12 minutes into. (b) recordActiveLessonPlayback (CourseVideoPage.jsx:233) force-pushes `getLessonPosition(...)`, which returns 0 for any lesson getLessonPosition judges finished (progress.js:94) — so replaying a finished lesson stamps position 0 with a fresh timestamp and nulls out duration_seconds on the row.

**Independent verification.** I reproduced the core defect against the unmodified `src/progress.js` (node + localStorage shim), and confirmed the surrounding call chain by reading every file in the path. The code is live on `release`.

WHAT IS CONFIRMED

1. The merge is timestamp-only. `src/progress.js:165-171` gates on `if (!priorPos || updatedAt > priorPos.at)` and never compares `position` against `priorPos.t`. Reproduced:
 - local 720s (12 min of a 40-min lecture) + remote row {position:0, duration:null, updatedAt:at+1} -> `getLessonPosition` returns 0, stored entry becomes `{"t":0,"d":null,...}`.
 - local 1800s + remote {position:30, updatedAt:at+1} -> resume becomes 30. Any newer row wins regardless of magnitude.
 This contradicts its own header (progress.js:151-156, "a row is applied only where it is more advanced than what is already on this device") and, more importantly, `CourseVideoPage.jsx:165-168`, which justifies pulling on EVERY course-page visit with "idempotent - mergeRemoteEntry only ever moves a video's position forward". That justification is false as written. The existing tests do not catch it: `progress.test.js:194-202` ("a newer remote row overwrites this device's older position") only ever tests newer+larger (100 -> 400), and :204-211 only tests older+smaller. The newer+smaller cell is untested.

2. The validation asymmetry is real and is the sharpest part of the finding. `recordLessonPosition` (progress.js:66-67) rejects a non-finite `seconds` and writes nothing; `progressSync.js:34` takes the same value and coerces it: `Number.isFinite(entry.position) ? Math.max(0, entry.position) : 0`. `recordLessonProgressReport` (CourseVideoPage.jsx:253 then 258-265) feeds both from the same variable. So a reading the local store deems unusable becomes a hard `position_seconds = 0, watched = true, updated_at = now()` on the server. Verified end-to-end in the repro: local correctly keeps 720, then the round trip through the merge sets it to 0. The throttle does not save this (progressSync.js:52 - a first-seen key has `?? 0`, so it pushes).

WHERE I PUSHED BACK / CORRECTIONS TO THE FINDING

- The lead trigger is the weakest link. Path (a) needs `player.getCurrentTime()` to RETURN `undefined` on a constructed-but-unready `YT.Player` rather than THROW - and `YouTubePlayer.jsx:117` swallows throws, which would kill that path silently. I could not prove YouTube's pre-ready behavior from here. That specific trigger is plausible, not proven.
- But the defect does not depend on it. Two triggers need no assumption about YouTube internals:

Compounding it, `startSeconds` (:206-209) is memoized on `[playlistId, activeVideoId]` and is never recomputed when the pull lands, so that device really does start at 0.
 (ii) The teardown flush is unconditional. `YouTubePlayer.jsx:228` and the `pagehide` listener at :122-123 call `reportProgress()` with no check that playback ever started - the repo's own test at `YouTubePlayer.test.jsx:115-130` confirms the unmount flush fires, and its fake player's default `getCurrentTime` is `() => 0`. This is gated entirely on being signed in - `queueProgressSync` and the pull both no-op without a `userId`, so the product's main flow (public no-login browsing) never reaches this code. Live production has exactly 1 row in `profiles` (verified via the anon key with `Prefer: count=exact`; `video_progress` correctly returns `Content-Range: */0` to anon, so owner-only RLS is working and I could not inspect real rows). No content-correctness, privacy, or security impact, and nothing student-authored is lost. Not "low", because it silently and unrecoverably corrupts the only per-student state the product keeps server-side, it breaks an invariant another module explicitly depends on, and it will scale with the account population that ratings/accounts just launched.

**Suggested fix.**

Fix the source first - the merge rule is secondary.

1. Stop manufacturing a zero (primary fix). `src/progressSync.js:34` - mirror the guard `recordLessonPosition` already applies, and drop the push instead of inventing a position:

```js
  if (!isSupabaseConfigured || !userId || !entry?.playlistId || !entry?.videoDbId) return;
  const position = Number(entry.position);
  if (!Number.isFinite(position) || position < 0) return; // never invent a 0
  ...
}
```
and in `pushNow`: `position_seconds: Math.max(0, Number(entry.position))`.

2. Never flush a position for a lesson that never played. `src/YouTubePlayer.jsx` already tracks `playbackRecorded` (line 91, set on first PLAYING). One line inside `reportProgress` kills the whole class:

```js
const reportProgress = () => {
  const player = playerRef.current;
  if (!player || !playbackRecorded) return;   // nothing played -> nothing to report
```
This makes both the cleanup flush (:228) and the `pagehide` flush (:122) honest, and also protects the LOCAL store, which currently accepts a `seconds: 0` flush.

3. Make the merge match its own documentation (defence in depth). `src/progress.js:166`:

```js
const priorPos = prev.positions?.[videoId];
const remoteT = Number(position) || 0;
const priorT = Number(priorPos?.t) || 0;
if (!priorPos || (updatedAt > priorPos.at && remoteT >= priorT)) {
```

If the team prefers last-write-wins, that is a defensible design - but then the comments at `progress.js:151-156` and `CourseVideoPage.jsx:166-167` must be corrected to say "last write wins by server timestamp", because `CourseVideoPage` currently justifies its per-visit pull with a guarantee the code does not provide. A middle ground that keeps rewatch working while blocking the corruption is to refuse only a regression to zero: `remoteT > 0 || priorT === 0`.

4. Close the race at `CourseVideoPage.jsx:229-236`: skip or defer the forced lesson-start push until `pullServerProgress` has resolved, and stop sending `duration: null` there - it nulls a known `duration_seconds` on an existing row.

Also add the missing test case to `src/progress.test.js` (the newer + smaller cell): local 720 with a newer remote row carrying position 0 must not leave `getLessonPosition` at 0.

**Independent verification.** The regex claim is literally true, but the harm it is priced on cannot occur in the code as it stands. Severity is badly overstated: high → low.

WHAT I CONFIRMED (executed, not reasoned):
Ran the real regex from src/lib/analytics.js:74 in Node. `userId`, `sessionId`, `ipAddress`, `userEmail`, `userName`, `authToken`, `deviceId` → all `false` (pass through); `user_id`, `email`, `session_token`, `ip`, `name` → all `true` (blocked). The `(^|_)…(_|$)` boundary genuinely only recognises snake_case, and this codebase is uniformly camelCase. So the deny-list is, as claimed, a form this project never writes. That much is real.

WHY I DID NOT CONFIRM THE FINDING AS FILED — three independent checks:

1. There is no sink, ever. `git grep setAnalyticsSink` over all tracked files returns exactly two hits, both inside analytics.js itself (line 20 comment, line 55 definition). `sink` is permanently `null`, so track() falls to the `else if (import.meta.env?.DEV) console.debug` branch — in a production build nothing is emitted anywhere at all.

2. There are no call sites. `git grep` for `lib/analytics|trackSearch|EVENTS\.` finds zero importers repo-wide. The only external mention of the module is a prose comment at src/lib/localStore.js:57. `track()` and `trackSearch()` are called nowhere but from each other. No test file exists for the module. It is dead code.

3. It is not even shipped. Grepping the existing build output for the module's own event literals (`search_result_selected`, `course_compare_added`) returns nothing in dist/ — Rollup tree-shakes it out entirely. The scrubber never runs in a student's browser.

The finding's own failure scenario is explicitly counterfactual — it opens "An integrator wires setAnalyticsSink(client) and … writes track(…, { userId })". Both halves are hypothetical future code. No student UUID is being forwarded to any third party today.

THE PRIVACY-POLICY CONTRADICTION IS ALSO NOT REAL TODAY. The live analytics is `@vercel/analytics/react` + SpeedInsights (src/App.jsx:24,27,269-270), which is genuinely cookieless aggregate page-view counting. PrivacyPolicy.jsx:143-153 discloses exactly that by name and then says "Beyond that, the current frontend contains no … third-party audience analytics integration" — which is currently accurate precisely because analytics.js has no sink and no callers. src/legalTruth.test.js:34 pins that wording. So the under-18 framing (PrivacyPolicy.jsx:168-176) does not attach to any current data flow.

WHAT IS LEGITIMATELY WRONG: the module header at lines 7 and 15-18 makes a strong, load-bearing promise — rules "enforced by this module rather than by convention", "No identifiers … It is a policy, not a side effect". For a file whose stated purpose is to be an integration point (line 20), shipping a guard that silently no-ops against the only naming convention the project uses is a real latent trap: the first integrator to wire a sink inherits a guarantee the code does not keep, and it fails open (forwards) rather than closed. That is worth fixing cheaply. It is not a live privacy incident, no student data is at risk, and it is not on any user-facing path — hence low, not high.

**Suggested fix.**

Make the key check camelCase-aware by normalising to snake_case before matching. In src/lib/analytics.js, replace line 74:

    if (/(^|_)(email|phone|mobile|name|user|session|token|ip|address)(_|$)/i.test(key)) continue;

with:

    // Normalise camelCase → snake_case so `userId` and `user_id` are treated alike.
    const norm = String(key).replace(/([a-z0-9])([A-Z])/g, "$1_$2").toLowerCase();
    if (/(^|_)(email|phone|mobile|name|user|session|token|ip|address|device|auth)(_|$)/.test(norm)) continue;

I validated this in Node against both directions. Now blocked: userId, sessionId, ipAddress, userEmail, userName, authToken, deviceId (plus the existing snake_case forms). Still kept: playlistId, chapterId, videoDbId, lastVideoId, queryLength, hasResults, resultCount, scope — i.e. content identifiers and shape metrics, which are the dimensions the module actually wants, remain usable. Note `device`/`auth` are added to the word list to cover deviceId/authToken; deliberately do NOT add a bare `id`, or it would strip the useful playlistId/chapterId dimensions.

Two cheap hardening additions worth pairing with it, since the module's value is entirely as a future integration point:
- Add a unit test asserting scrub() drops camelCase identifier keys — otherwise this regression is invisible again the moment someone edits it (there is currently no test file for this module at all).
- Consider deleting the module instead. It has zero importers, zero call sites, no sink, and is tree-shaken out of the bundle; if no analytics integration is actually planned, removing it eliminates the misleading "enforced by this module" header outright and is the lower-maintenance option.
